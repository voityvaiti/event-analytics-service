# Read testing — `/api/v1/stats` latency

Tracks how long the analytics reads take against a realistically populated
table, so a query regression shows up as a number rather than as a slow
dashboard someone eventually complains about. One directory per endpoint; they
share the scenario ([`stats-read.js`](./stats-read.js)) and the measuring
routine ([`measure-read.sh`](./measure-read.sh)), because the cells differ only
in the URL they call.

Latency is the headline, not throughput. An analytics read costs tens to
hundreds of milliseconds against the ~2ms an insert takes, and a regression here
looks like a query getting slower, not like the service accepting fewer of them.

## What the run does

Every request is a question generated by
[`lib/query-generator.js`](../lib/query-generator.js) — the read-side
counterpart to the event generator on the write side. What varies on a read is
not a payload but the question, so that is what it diversifies:

- **Window size** is drawn from a skewed mix — 1h, 1d, 7d, 30d — because
  analytics traffic is mostly "the last hour" and "today" with a thinner tail of
  weekly and monthly reports.
- **Window position** favours recent data by a 1/rank law, the same shape page
  traffic follows, with a tail that still reaches the start of the corpus.

Both are pure functions of the iteration number. Two runs ask the identical
sequence of questions, which is what makes an A/B — with an index and without
one, before a change and after it — a comparison of one variable.

## Reading a journal row

Rows carry the usual rig and config stamps (CPU, cores, pool, schema,
`start_rows`), plus two things specific to reads.

- **`windows`** — latency split by window size. The split is the point: those
  sizes differ by more than an order of magnitude in the rows they touch, so a
  single figure would describe hour-long questions in its median and month-long
  ones in its tail. A regression in one size and not the others is a real and
  common shape.
- **`index_scans` / `seq_scans`** — how many index and sequential scans the run
  actually caused, counted from Postgres over the queries the app really ran.
  They keep a flat latency result from being ambiguous: they say outright
  whether the planner reached for the index or swept the table instead. Zero
  index scans with the index in place means the planner declined it, which is a
  different problem from an index that did not help.

## Why the corpus matters here

Reads are the reason the suite seeds a corpus at all (see the
[suite README](../README.md)): on an empty table the planner ignores the very
indexes these tests exist to exercise, so any number measured there would be
fiction. The window a request asks for is a small slice of that corpus by
design — a window covering most of it would be cheaper to sweep than to look up,
and the index would never be chosen.
